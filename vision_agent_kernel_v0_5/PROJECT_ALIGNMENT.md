# Sparkle Project: 视觉交互 Agent 内核与伴游系统设计白皮书

> **文档受众**：后续参与本项目的自动化代码 Agent / 架构师
> **文档目的**：传递项目核心价值观、非代码层面的架构意图、产品形态以及机制设定。不要从代码仓库反推这些概念，所有新增代码必须符合本对齐文档的哲学。

## 一、 产品愿景与系统边界 (Product Vision & Boundary)

### 1.1 产品定义

本项目不是一个传统的"按键精灵"、死板的"自动化测试脚本"，也不是简单的"LLM 调接口工具"。
本项目的终极形态是：**一个面向 ACG（二次元）玩家的桌面端赛博伴游（Desktop Companion）与具身智能控制中枢。**
它具有角色的情绪化外壳（如 Live2D/语音气泡交互），内里则是一套极度硬核的 3D 视觉感知与动态状态机执行内核。

### 1.2 系统边界与安全红线 (CRITICAL)

* **绝对禁止**：编写用于破坏线上游戏公平性、绕过商业反作弊系统、读取/修改游戏内存、驱动级底层注入的代码。
* **运行环境**：本系统的物理输入与 3D 视角控制能力，仅限于**授权的 3D 沙盒、自建 ARPG 测试环境（如 Unity/Godot）、QA 环境或单机研究环境**中运行。

## 二、 用户体验与产品形态 (Productization & UX)

本系统的外壳（GUI）基于 `Tauri + React + Python FastAPI` 架构，必须向用户提供以下核心体验：

### 2.1 陪伴式交互 (Persona-Driven UI)

* **情绪化呈现**：摒弃冷冰冰的"日志报错"。底层抛出的 `TARGET_LOST`（目标丢失）或 `OBSTACLE_BLOCKING`（障碍卡死），应由大模型转化为角色的语音或气泡（例："哎呀，怪物跑到哪里去了？"）。
* **自然语言控制**：用户可以直接通过语音或文字下达任务，大模型（GLM / MiniMax）将语义转化为底层的 `TaskSpec`，并以伴游角色的口吻回复确认。

### 2.2 锚点对齐的 ROI 校准 (Anchor-Based Calibration)

* **多端适配痛点**：由于分辨率不同，纯相对比例框选会导致 UI 识别漂移。
* **解决方案**：GUI 提供的屏幕校准向导必须支持**锚点锁定**（Top-Left, Bottom-Right 等）。底层存储的 Profile 不是单纯的比例，而是 `[Anchor + Offset + Size]`，以确保在不同分辨率和带鱼屏下的绝对稳定性。

### 2.3 可视化技能编辑与沙盒校验 (Visual Skill Editor & Dry-Run)

* **告别黑盒**：用户录制的动作序列（Skill）必须在 GUI 中以时间轴和节点的形式呈现。用户可动态编辑前置条件、视觉触发器和失败回退分支（Fallback）。
* **沙盒模拟校验**：任何由大模型生成的任务图或用户修改的 Skill，在投入真实执行前，必须在系统内部进行一次 Dry-Run Sandbox Simulation（状态机空转校验），防止参数错误或条件死锁。

## 三、 大脑与脊髓：核心战斗与控制机制 (The Brain-Spine Dichotomy)

面对极高要求的 3D ARPG 战斗场景，系统采用**大小脑极度分离**的控制哲学：

### 3.1 脊髓反射层：毫秒级实时微观控制 (The Reflex)

* **完美闪避 (Perfect Dodge)**：这是生存的底座。本地轻量级视觉模型（YOLO）不仅识别目标，还专门识别"怪物攻击前摇"或"范围警示（红光/红圈）"。一旦触发，底层直接抛出最高优先级 `P0 Interrupt`，瞬间切断当前连招，下发闪避指令，0.5秒后自动恢复连招。
* **FOV 摄像机伺服 (FOV-Aware Servo)**：禁止在 3D 环境使用 2D 像素误差线性移动鼠标。必须结合游戏 FOV，将像素误差转化为偏航角（Yaw）和俯仰角（Pitch），结合死区和速度前馈（Feedforward），实现平滑如真人的视角锁定（拉枪）。

### 3.2 战术大脑层：大语言模型的战前与逆风干预 (The LLM Brain)

* **战前排兵布阵**：大模型（GLM/MiniMax）不参与毫秒级战斗操作。它在战前根据玩家阵容配置，生成一份**战斗逻辑图（Combat Playbook Graph）**（如：默认输出循环 -> 大招就绪高优触发 -> 血线濒危兜底切人）。
* **战中休眠与逆风唤醒**：战斗开始后大模型休眠，交由本地状态机按逻辑图执行。只有当挫败感（Frustration）飙升或角色死亡时，系统才会唤醒大模型，截取画面寻求策略变更。

## 四、 内核运转哲学：五平面架构 (The 5-Plane Architecture)

代码实现分为五个绝对解耦的平面，任何跨平面的通信**只能通过线程安全的 `StateBus`（状态总线）或事件队列**，禁止直接调用。

1. **Perception Plane (感知平面 - 高频)**：
* 包含 DXcam 高频抓帧、YOLO 检测、BoT-SORT 追踪、以及低频的深度估计（Depth/Obstacle）。只负责输出结构化观察结果（Observation），**绝对不做任何决策**。


2. **Control Plane (控制平面 - 中频)**：
* 读取追踪数据（TargetTrack），计算基于趋势窗口的进度（Progress）和挫败感（Frustration）。
* 将意图（CameraIntent / MovementIntent）下发，并在无进度时抛出中断（Interrupt）。


3. **Execution Plane (执行平面 - 严格时序)**：
* **Input Lease (输入租约)**：所有按键指令必须带有过期时间（expires_at）。
* **Deadman Switch (死人开关)**：任何线程假死、失焦或超时未续租，必须立刻强制释放所有按键（Release All），彻底杜绝按键泄漏。


4. **Orchestration Plane (编排平面 - 低频/事件驱动)**：
* 图结构（Graph-based）长程任务流转。响应底层的 SkillResult 和异常。
* 所有在 3D 空间里的复杂行为（如战斗），必须被封装为带有视觉触发器（Visual Triggers）的动作块（ActionBlock），而非傻等时间的死脚本。


5. **Telemetry Plane (遥测平面 - 异步)**：
* 高频数据（如稳态观察）进行降采样记录。中断、状态跳变等关键事件 100% 记录为 JSONL。
* 引入 NVENC 或极简硬件录制形成视频流，方便复盘时 LLM 结合 JSONL 进行时空对齐分析。

## 五、 给 Coding Agent 的开发铁律 (Developer Commandments)

在阅读或修改具体代码时，必须时刻铭记以下原则：

1. **拒绝阻塞等待**：任何需要等待的操作（尤其是 UI 冷却或动画等待），必须被切分为 Chunked Wait（如 50ms 一次循环），并在循环内检查 `StateBus` 中的高优异常。禁止使用大块 `time.sleep()`。
2. **拒绝单帧差值**：任何对于"进度（Progress）"或"是否卡住"的判断，禁止只比较当前帧与上一帧。必须使用时间窗口趋势（如过去 2 秒的斜率）来抗击视觉抖动。
3. **统一单调时钟**：全系统禁止使用 `time.time()` 进行逻辑判断。所有超时、延迟计算、租约过期必须使用 `time.perf_counter()`。
4. **保持 LLM 的权威与克制**：不要让大模型去决定光标向左移动几个像素，只让大模型决定"下一步优先释放哪个技能"。
5. **始终拥抱不确定性**：所有的动作设计必须预留 Fallback。系统默认"这个操作可能会失败"，并始终依赖闭环的视觉反馈（Visual Checkpoint）来推进状态节点。
