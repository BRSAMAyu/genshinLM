## 第一章：验证层次体系

验证金字塔按成本/覆盖率的倒三角形组织，从底部到顶部呈漏斗形：

```
                    ★ 里程碑验证 (Milestone)
                     ─── 最少，最重
                 ★★★★ 场景验证 (Scenario)
                    ─── 较少
              ★★★ 集成验证 (Integration)
                 ─── 中等
            ★★ 单元验证 (Unit)
               ─── 最多，最细
```

### 1.1 单元验证 (Unit)

**定位**：测试金字塔的最底层，数量最多，粒度最细。

| 属性 | 定义 |
|------|------|
| 测试数量目标 | 每个能力ID对应 2-5 个单元测试，总计约 170-180 个（感知~50、输入~20、导航~15、UI~30、战斗~25、探索~20、对话~10、其他~15） |
| 覆盖范围 | 单个能力的独立功能验证 |
| 输入 | 模拟的感知数据（截图/YAML配置/pytest fixtures） |
| 输出 | 预期的操作响应或状态变化 |
| 环境依赖 | 无需真实游戏，100% 模拟 |
| 典型示例 | 给定一张菜单截图，验证 OCR 能正确读取文字 |

**通过标准**：
- 单次执行准确率 ≥ 95%（精确类能力）
- 单次执行延迟 ≤ 阈值（实时类能力，如战斗检测 ≤ 100ms）
- 单次执行成功率 ≥ 80%（策略类能力，如元素反应选择）

**执行频率**：每次代码变更 → 自动触发（CI 流水线）

### 1.2 集成验证 (Integration)

**定位**：测试金字塔的第二层，验证多个能力的协同工作。

| 属性 | 定义 |
|------|------|
| 测试数量目标 | 每个子步骤对应 1-3 个集成测试，总计 ~50 个 |
| 覆盖范围 | 场景文档中的单个子步骤（如"打开角色面板→选择角色→点击升级"） |
| 输入 | 模拟的感知数据 + 部分真实操作反馈 |
| 输出 | 完整的操作链执行结果 |
| 环境依赖 | 可能需要录屏数据作为输入（无需实时游戏） |
| 典型示例 | 导航至 NPC → 按 F 对话 → 检测对话选项 → 选择第一个选项 |

**通过标准**：
- 单步操作成功率 ≥ 90%
- 连续 3 步无错误完成 ≥ 85%

**执行频率**：每日运行（CI 流水线 + 定时任务）

### 1.3 场景验证 (Scenario)

**定位**：测试金字塔的第三层，验证完整场景的端到端流程。

| 属性 | 定义 |
|------|------|
| 测试数量目标 | 每个场景对应 1 个端到端场景测试，总计 ~30 个 |
| 覆盖范围 | 完整游戏场景（日常循环、Boss战、角色升级、探索解谜） |
| 输入 | 录屏回放或沙盒环境的实时感知数据 |
| 输出 | 场景完成状态（成功/失败/部分完成） |
| 环境依赖 | 沙盒游戏环境（测试账号） |
| 典型示例 | 从蒙德出发，完成4个每日委托，返回凯瑟琳领奖 |

**通过标准**：
- 基础场景（日常/UI）：连续 5 次无错误完成
- 中等场景（探索/解谜）：连续 3 次无错误完成
- 困难场景（Boss战）：3 次中成功 2 次

**执行频率**：每周运行（沙盒环境）

### 1.4 里程碑验证 (Milestone)

**定位**：测试金字塔的顶层，数量最少但权重最高。

| 属性 | 定义 |
|------|------|
| 测试数量目标 | 每个里程碑对应 1 个里程碑测试，总计 ~10 个 |
| 覆盖范围 | 跨多个场景的长时间运行验证（如"蒙德序章全流程"） |
| 输入 | 生产环境的实时感知数据 |
| 输出 | 里程碑完成状态 + 性能指标 |
| 环境依赖 | 真实游戏环境 + 人类监督 |
| 典型示例 | 从新号开始，完成蒙德序章全部内容 |

**通过标准**：
- 必须在生产环境中执行
- 连续 2 次端到端完成
- 总耗时不超过预期的 1.5 倍
- 无 P0/P1 级别错误

**执行频率**：每个里程碑节点（生产环境 + 人工监督）

### 1.5 各层验证总览

| 层次 | 测试数量 | 环境要求 | 执行频率 | 通过门槛 | 覆盖率目标 |
|------|----------|----------|----------|----------|------------|
| 单元验证 | ~160 个 | 纯模拟 | 每次变更 | 95% / 100ms / 80% | 100% 能力覆盖 |
| 集成验证 | ~50 个 | 模拟+录屏 | 每日 | 90% 单步 / 85% 三步 | 80% 子步骤覆盖 |
| 场景验证 | ~30 个 | 沙盒环境 | 每周 | 5/5 / 3/3 / 2/3 | 60% 场景覆盖 |
| 里程碑验证 | ~10 个 | 生产环境 | 里程碑节点 | 2/2 + 无P0/P1 | 100% 核心里程碑 |

## 第三章：测试环境策略

### 3.1 纯模拟环境 (Dry-run)

**定位**：成本最低、速度最快的测试环境。

**环境特征**：
- 使用预存截图/录屏作为感知输入
- 不操作真实游戏（`ConsoleInputBackend`）
- 所有数据均为模拟数据

**适用场景**：
- 单元测试（100% 覆盖）
- 集成测试中的独立能力验证（80% 覆盖）
- 开发阶段快速验证

**资源需求**：
- 截图数据集（按场景/状态分类，≥ 500 张）
- YAML 配置文件（模拟感知结果）
- pytest fixtures（可复用测试数据）

**执行效率目标**：单次单元测试 ≤ 500ms

### 3.2 录屏回放环境 (Replay)

**定位**：平衡成本与真实度的测试环境。

**环境特征**：
- 录制真实游戏操作的视频（按帧存储）
- 按帧回放作为感知输入
- 输入操作不执行（仅记录决策）

**适用场景**：
- 集成测试（60% 覆盖）
- 场景测试中的已知路径验证

**资源需求**：
- 录屏数据集（按场景分类，≥ 50 个场景）
- 帧级标注数据（敌人位置、UI状态、对话内容）
- 回放引擎（读取录屏+模拟决策）

**执行效率目标**：单次录屏回放测试 ≤ 30s

### 3.3 沙盒游戏环境 (Sandbox)

**定位**：真实但低风险的测试环境。

**环境特征**：
- 在专用测试账号上运行真实游戏
- 仅在低风险区域（蒙德城内、已完成区域）
- 可执行真实操作

**适用场景**：
- 集成测试（40% 覆盖）
- 场景测试（60% 覆盖）

**资源需求**：
- 测试账号（≥ 1 个）
- 专用测试机器（最低配置：GTX 1060 / 8GB RAM）
- 自动化截图/录屏工具
- 异常恢复脚本（卡死检测、自动重启）

**执行效率目标**：单次场景测试 ≤ 10 分钟

### 3.4 生产环境 (Production)

**定位**：最真实但成本最高的测试环境。

**环境特征**：
- 真实账号、真实游戏
- 全场景覆盖
- 必须有人类监督

**适用场景**：
- 里程碑测试（100% 覆盖）
- 极端场景验证（深境螺旋 11-12 层）

**安全措施**：
- `SafeWindowInputBackend`（窗口焦点保护）
- 紧急停止按钮（F9 / Ctrl+C）
- 看门狗超时自动停止
- 人工监督员实时监控

**执行效率目标**：单次里程碑测试 ≤ 预期时间的 1.5 倍

### 3.5 测试环境总览

| 环境层级 | 真实度 | 执行速度 | 成本 | 覆盖率目标 | 执行频率 |
|----------|--------|----------|------|------------|----------|
| Dry-run | 0% | 最快 | 最低 | 100% 单元 | 每次变更 |
| Replay | 30% | 快 | 低 | 60% 场景 | 每日 |
| Sandbox | 70% | 中 | 中 | 40% 场景 | 每周 |
| Production | 100% | 慢 | 高 | 100% 里程碑 | 里程碑节点 |

## 第四章：通过标准定义

### 4.1 单项能力通过标准

能力按类型分为三类，通过标准各不相同：

#### 精确类（Precision）

**定义**：结果必须与标准值高度一致，不允许明显偏差。

| 等级 | 准确率要求 | 适用能力示例 | 漏检/误检策略 |
|------|------------|--------------|---------------|
| A 级 | ≥ 98% | UI按钮检测、Boss阶段转换、加载画面检测 | 宁可误报不漏报 |
| B 级 | ≥ 95% | 敌人检测、对话选项、元素附着 | 误报触发重试 |
| C 级 | ≥ 90% | 宝箱类型、地图文字OCR | 误报容错处理 |

#### 实时类（Real-time）

**定义**：必须在时间限制内完成，否则失去意义。

| 等级 | 延迟要求 | 适用能力示例 | 超时策略 |
|------|----------|--------------|----------|
| 关键 | ≤ 50ms | 危险检测、反射闪避 | 超时触发保守策略 |
| 标准 | ≤ 100ms | 敌人检测、HP读取 | 超时触发重试 |
| 宽松 | ≤ 200ms | 场景整体理解、谜题识别 | 超时跳过非关键步骤 |

#### 策略类（Strategic）

**定义**：结果不必完美，但整体方向必须正确。

| 等级 | 成功率要求 | 适用能力示例 | 失败策略 |
|------|------------|--------------|----------|
| 严格 | ≥ 85% | 元素反应选择、路径规划 | 失败后重试3次 |
| 标准 | ≥ 80% | Boss机制应对、深境增益选择 | 失败后使用默认策略 |
| 宽松 | ≥ 75% | 极限战斗、极限解谜 | 失败后退出场景 |

### 4.2 场景通过标准

场景按难度分为四档，通过标准递增：

#### 基础场景（日常/UI）

**定义**：操作步骤明确、环境变化小、人工介入频率低。

| 场景示例 | 最低连续成功次数 | 总成功率要求 | 最大错误数 |
|----------|------------------|--------------|------------|
| 每日委托×4 | 5次 | ≥ 90% | 2次/次 |
| 角色升级 | 5次 | ≥ 95% | 1次/次 |
| 秘境领奖 | 5次 | ≥ 95% | 1次/次 |
| 锻造/合成 | 5次 | ≥ 95% | 1次/次 |

#### 中等场景（探索/解谜）

**定义**：操作步骤较明确、环境有一定变化、人工可能需要介入。

| 场景示例 | 最低连续成功次数 | 总成功率要求 | 最大错误数 |

## 第七章：回归测试策略

### 7.1 回归测试集定义

**一级回归（每次必跑）**：
- 核心冒烟测试（ScreenState、InputExecution、Dialog、EmergencyStop）
- 紧急停止功能（死人开关、F9、Ctrl+C）
- 窗口焦点保护

**二级回归（每日必跑）**：
- 全部感知能力单元测试
- 全部输入能力单元测试
- 关键UI操作流程测试
- 对话系统测试

**三级回归（每周必跑）**：
- 场景验证测试（沙盒）
- 战斗能力测试
- 探索/解谜测试

### 7.2 回归测试优先级

**高优先级（易退化）**：

1. 输入执行层（I-01 ~ I-09）
   - 原因：底层依赖，系统调用层
   - 风险：任何代码变更都可能影响

2. 感知层（屏幕状态检测 P-01）
   - 原因：上游数据源，影响下游所有决策
   - 风险：UI 更新可能导致检测失效

3. 紧急停止功能（I-06、I-07）
   - 原因：安全关键功能
   - 风险：功能退化可能导致事故

**中优先级**：

4. 对话系统（D-01 ~ D-09）
   - 原因：版本更新可能改变对话框样式
   - 风险：游戏版本更新后对话流程可能变化

5. Boss 阶段检测（P-09）
   - 原因：Boss 战核心依赖
   - 风险：不同 Boss 外观差异大

**低优先级（稳定）**：

6. 角色养成 UI 操作（U-23 ~ U-29）
   - 原因：UI 结构稳定，操作流程固定
   - 风险：UI 风格更新时需调整

7. 探索解谜（E-10 ~ E-15）
   - 原因：解谜机制相对稳定
   - 风险：区域更新时需添加新解谜类型

### 7.4 测试维护

**随能力增加的测试维护**：

1. **能力分级**：
   - P0 能力：必须 100% 覆盖（每个能力 ≥ 2 个测试）
   - P1 能力：必须 90% 覆盖（每个能力 ≥ 1 个测试）
   - P2 能力：尽量覆盖（按优先级添加）

2. **测试集淘汰**：
   - 能力删除 → 删除对应测试
   - 能力合并 → 合并对应测试
   - 能力重构 → 更新测试描述

3. **测试数据更新**：
   - 游戏版本更新 → 收集新截图/录屏
   - UI 变化 → 更新标注数据
   - 能力升级 → 更新预期输出

4. **测试质量评估**：
   - 每月评估测试通过率趋势
   - 移除长期稳定的测试（减少维护负担）
   - 合并重复测试（提高效率）

```python
            5. 记录结果
        """
        # 1. 准备输入数据
        input_data = test_config.input_data

        # 2. 执行被测能力（以屏幕状态检测为例）
        from perception.genshin_screen_classifier import ScreenStateClassifier
        classifier = ScreenStateClassifier()
        output = classifier.classify(input_data["screenshots"])

        # 3. 比较输出与预期
        expected = test_config.expected_output

        # 4. 验证通过条件
        accuracy = calculate_accuracy(output, expected)
        assert accuracy >= test_config.pass_criteria["accuracy"], \
            f"准确率 {accuracy} < {test_config.pass_criteria['accuracy']}"

        # 5. 记录结果
        record_test_result(
            test_id=test_config.test_id,
            status="PASSED",
            metrics={"accuracy": accuracy}
        )
```
