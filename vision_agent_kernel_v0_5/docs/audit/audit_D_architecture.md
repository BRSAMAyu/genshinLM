## 详细发现

### D1: GENSHIN_ERROR_RECOVERY_ARCHITECTURE.md

#### [P1] 重要问题

**1. 全局恢复状态机遗漏状态转移**

第2章状态转移表（第206-217行）中存在遗漏：

```
文档定义:
("NORMAL", "interrupt_received"): "ANOMALY"
("ANOMALY", "diagnosis_complete"): "DIAGNOSE"
...

但缺少以下合法转移:
- ("NORMAL", "manual_recovery_request"): 应进入 PLAN 而非 ANOMALY
- ("DIAGNOSE", "diagnosis_failed"): 应返回 ANOMALY 而非死锁
- ("PLAN", "planning_timeout"): 应进入 ESCALATE
- ("RECOVER", "partial_success"): 应允许重试而非立即升级
```

**2. P2 中断优先级数值错误**

第94-117行代码示例：
```python
Interrupt(
    priority=2,  # ❌ 错误：应为 20-30 之间
    code="TARGET_LOST",
    ...
)
```
实际代码中 Interrupt 的 priority 是 int 类型，2 是合法值，但与第91-92行的严重性分级表矛盾：
- CRITICAL (P0): 0
- SEVERE (P1): 10
- MODERATE (P2): 20-30
- MINOR (P3): 40-100

建议统一为 `priority=25` 以表示 MODERATE 级别。

#### [P2] 建议

**3. 8个级联案例中部分场景过于理论化**

案例5-8（感知偏差、版本更新弹窗、死亡循环、任务条件变更）缺少具体的检测点量化指标。例如：
- 案例5 E3描述"错误决策（基于错误目标）→ 雪崩式失败"，但未给出雪崩触发的具体条件阈值
- 案例8 E2描述"基于旧信息重试 → 失败"，但未说明如何区分"版本变更导致的失败"和"普通操作失败"

**4. 附录A错误码有重复分类**

错误码表中：
- `NETWORK_DISCONNECT`: 在P0和P1行都出现（行1305和行1314），但触发条件和恢复配方不同，应明确区分"临时断开(<30s)"和"完全断开(>=30s)"。

#### [P2] 建议（低优先级）

**5. 附录C超时预算表与正文不一致**

正文第247-250行的超时阈值：
- 死锁检测: 30s
- 状态卡死: 30s

附录C（行1340-1354）缺少对应的恢复类型行项目，应补充 "STUCK_RECOVERY" 的超时预算。

### D5: GENSHIN_IMPLEMENTATION_ROADMAP.md

#### [P1] 重要问题

**1. 工时估算合计与分项累加存在算术错误**

第688行 M0合计显示52天：
- 实际分项累加：3+2+2+4+2+3+5+4+4+4+2+2+1+2+2+2+3+2+2+4+6+5+5+4+4+4+4+4 = **95天**

第747行 M1合计显示162天，实际需重新核算。

第861行 M3合计显示240天，第951行 M5合计显示"约200天"，但第948行Track F分项估算为150天。

**建议：重新验证所有里程碑的工时累加。**

**2. 第7.1章人月估算（行1436-1451）与分项工时不符**

文档声称：
- M0: 52天/人月2.2
- M1: 162天/人月10.8
- 总计: 951天/62.1人月

但按2人并行计算（文档第1450行"双人或以上并行"）：
- M0 52天 → 26人月（2人）× 1 = 2.2人月 ❌ 错误
- M1 162天 → 81人月（2人）... 不匹配

实际计算应为：
- M0: 52天/30 = 1.7人月（非2.2）
- M1: 162天/30 = 5.4人月（非10.8）

**3. 甘特图关键路径计算有误**

第1461-1474行定义的关键路径：
```
M0(52天) → M1(162天) → M3-C战斗(240天) → M4(139天) → M5(200天)
路径长度: 52+162+240+139+200 = 793天
```

但按第977-1000行的并行开发图，M2（日常循环）与M3可部分并行，M3的C战斗模块（Track D1）可与M4部分并行。

关键路径应为：M0(52) → M1(162) → M3非战斗部分 → M4 → M5，而非全部串行。

#### [P2] 建议

**4. Top 10风险的风险等级评估主观性过强**

风险1-10的评估（"概率"、"影响"）缺乏量化依据。

例如风险1"实时战斗的操作精度"：
- 概率标注为"中 (40%)"，但未说明40%如何得出
- 缓解策略过于泛泛（如"建立Boss机制知识库"），缺少具体的实现方案

**建议为每个风险添加历史数据支撑或专家评估依据。**

**5. 附录E里程碑检查点缺少验收门槛的量化指标**

例如M0检查点（行1675-1682）：
```
□ P-01 屏幕状态分类准确率≥95%
□ P-06 对话框检测召回率≥99%
```

缺少：
- 如何测量"召回率≥99%"（需要多少测试样本）
- 如何判定"连续5次蒙德导航成功"（行1689）中的"成功"标准

**6. 附录A能力依赖图（行1517-1555）中部分能力ID缺失**

图中展示的依赖链不完整，例如：
- P-05(交互提示) → D-07(NPC交互) 缺少P-05的完整定义
