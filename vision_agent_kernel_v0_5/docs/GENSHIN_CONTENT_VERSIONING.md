# 原神内容版本适配层文档
# Genshin Impact Content Versioning Layer

> **文档定位**: 本文档定义了 Sparkle Project Agent 如何适应原神每42天一次版本更新的完整机制。
> 包括变更分类、检测策略、适配框架、版本迁移流程和持续学习机制。
> **所有能力仅限于授权3D沙盒 / 自建ARPG测试环境 / QA单机研究环境。**

---

## 第一章：版本变更分类

原神版本变更按影响深度分为四层：UI层、机制层、内容层、系统层。不同层次的变更需要不同的适配策略和响应速度。

### 1.1 UI层变更

UI层变更是指游戏界面元素的位置、样式、布局发生的改变。这类变更的特点是发生频率高（每个大版本都可能涉及）、影响范围局部、对Agent感知系统影响最大。

**按钮位置移动**：这是最常见的UI变更类型。例如游戏设置菜单的某个选项按钮从上版本的位置(860, 580)移动到了(920, 610)。这类变更会导致Agent基于坐标记忆的点击操作完全失效。检测难度为低，因为可以通过模板匹配或OCR识别按钮的存在性，但定位需要重新校准。处理策略是采用相对坐标系统，以界面特征元素为锚点计算目标按钮的偏移量，而不是依赖绝对像素坐标。

**新增/删除菜单项**：例如在4.0版本中，枫丹的设置菜单新增了"水下渲染"选项。这类变更可能导致Agent的导航路径失效，如原本按顺序点击设置菜单的第5项变成了第6项。检测难度为中，需要验证预期路径上的每个元素是否存在。处理策略是维护每个菜单的版本快照，当检测到菜单结构不符时触发重新学习流程。

**图标样式变更**：例如圣遗物强化的材料图标在4.3版本进行了重新设计。这类变更会影响基于图标模板匹配的检测器。检测难度为高，因为细小的视觉差异可能导致检测器误判。处理策略是使用多尺度特征匹配，结合语义描述而非精确像素匹配。

**分辨率/布局调整**：例如游戏在不同分辨率下UI元素的相对位置不同，或者同一分辨率下UI缩放比例发生变化。检测难度为低，通过已知的锚点元素可以快速检测。处理策略是存储每个分辨率的配置档案，运行时根据检测到的分辨率选择对应配置。

### 1.2 机制层变更

机制层变更是指游戏核心玩法的规则、元素反应、系统机制发生的改变。这类变更的特点是影响Agent的战斗策略和任务执行逻辑，需要深度理解才能正确适配。

**新元素/新反应**：最典型的案例是3.0版本引入的草元素和激化反应体系。在此之前，Agent只需要处理风、火、水、雷、冰、岩七种元素反应，添加草元素后，Agent需要理解草+雷=激化、草+水=绽放、草+火=燃烧等全新反应链。检测难度为高，因为新元素可能带来全新的视觉表现（如草元素反应产生的草原、海克斯霸等）。处理策略是为每种新元素反应建立视觉特征库，并更新战斗决策树的元素分支。

**新战斗机制**：例如4.0版本引入的芒荒机制。枫丹的部分怪物具有芒或荒的属性，使用相反属性攻击可以使怪物瘫痪。这意味着Agent在面对枫丹怪物时需要识别其芒荒属性并选择对应属性的角色或攻击方式。检测难度为高，因为芒荒属性的视觉表现相对微妙，且只在枫丹区域生效。处理策略是建立芒荒属性的视觉识别模型，并将其整合到战斗决策流程中。

**新探索机制**：例如5.0版本引入的夜魂机制。纳塔角色可以通过元素战技进入夜魂加持状态，夜魂值耗竭后会消耗燃素来维持。夜魂传递机制允许在特定移动状态下切换纳塔角色直接进入夜魂加持状态。检测难度为高，夜魂相关的UI元素和视觉表现都是全新的。处理策略是为每种纳塔角色建立夜魂状态机，包括状态识别、状态转换和能量管理。

**新UI系统**：例如4.4版本上线的圣遗物快速装备功能，改变了圣遗物管理界面的布局和交互流程。5.5版本引入的"祝圣之霜"机制定义了新的圣遗物强化流程。检测难度为中，需要验证新UI是否出现在预期位置。处理策略是维护每个UI系统的版本模板，遇到新版本时触发界面扫描和模板更新。

### 1.3 内容层变更

内容层变更是指游戏世界中的具体实体（区域、角色、物品、任务、Boss）发生的增加或改变。这类变更的特点是数量大、更新频繁，但对Agent核心功能的影响相对较小。

**新区域开放**：例如2.0稻妻、3.0须弥、4.0枫丹、5.0纳塔的开放。新区域意味着新的地形、新的传送点、新的NPC位置、新的资源分布。检测难度为低，区域名称可以通过版本号或游戏内API获取。处理策略是按区域管理内容数据库，包括区域内的采集物位置、传送点坐标、NPC位置等信息，新区域开放时通过探索自动填充或人工导入。

**新角色/武器/圣遗物**：每个版本都会推出新角色及其配套武器和圣遗物。Agent需要知道新角色的技能特效以进行视觉识别，需要知道新武器的效果以进行配装推荐。检测难度为低，内容数据可以通过官方公告或数据库同步获取。处理策略是建立内容数据与代码分离的架构，新内容通过配置或补丁包注入，无需修改核心代码。

**新任务/活动**：每个版本都会推出限时活动和新的世界任务。这类内容对Agent的日常运行影响较小，但可能在自动化任务执行时遇到。检测难度为中，任务目标可能因版本更新而改变。处理策略是将任务系统设计为可扩展的，每遇到新任务时动态学习目标识别和执行策略。

**新Boss/新怪物类型**：每个大版本都会引入新的世界Boss和精英怪物。这些怪物可能有独特的机制或外观，需要Agent能够识别并制定相应策略。检测难度为中，新怪物的视觉特征需要采集和学习。处理策略是为新怪物建立检测模板，并更新战斗策略库。

### 1.4 系统层变更

系统层变更是指游戏底层技术、客户端架构、网络协议等方面的改变。这类变更的特点是发生频率低，但一旦发生影响范围极广，可能导致整个Agent系统失效。

**性能优化**：版本更新可能带来帧率变化、加载速度变化等。这类变更会影响Agent的时序判断，如原本每60帧检测一次的操作可能因帧率提高而需要调整检测间隔。检测难度为低，通过对比版本前后的性能指标可以发现。处理策略是使用相对时间而非帧数作为时序基准，避免依赖固定的帧率假设。

**反作弊更新**：原神的反作弊系统(mhyprot2.sys)可能随版本更新而变化。这类变更可能影响Agent的屏幕截取和输入操作。检测难度为高，需要实际测试才能确认。处理策略是保持与游戏客户端的松耦合连接，任何反作弊相关操作都应保持在OS级别而非内核级别，避免触发检测。

**网络协议变更**：版本更新可能带来客户端与服务器之间通信协议的变化。这类变更主要影响需要与服务器交互的功能。检测难度为高，需要分析网络流量才能发现。处理策略是避免依赖游戏网络协议，保持完全的客户端本地操作。

**文件结构变更**：版本更新可能改变游戏资源的文件结构，如UI资源、配置文件的存储位置。这类变更影响基于文件分析的检测器。检测难度为中，文件结构的变化通常会在资源包中体现。处理策略是使用版本化的资源解析器，根据检测到的游戏版本选择对应的解析逻辑。

## 第二章：变更检测机制

Agent通过主动检测、被动检测和外部信号三种途径发现版本变更。这三种途径相互补充，形成完整的检测覆盖网络。本章详细描述每种检测途径的具体实现方式和触发条件。

### 2.1 主动检测

主动检测是Agent周期性地执行的验证操作，目的是在用户发现问题之前主动发现版本变更。主动检测的优势在于可以在问题出现之前就做出响应，避免因版本变更导致的连续操作失败。

**启动时版本验证**：Agent在启动时首先检测游戏的版本号。版本号可以通过读取游戏进程信息、解析游戏窗口标题或OCR识别启动界面获取。验证流程包括以下步骤：

1. 获取当前游戏版本号（例如从窗口标题"原神 5.7"中提取"5.7"）
2. 与Agent维护的已知版本列表对比
3. 如果版本号不在已知列表中，说明可能是新版本，触发版本变更评估流程
4. 如果版本号已知但对应的适配状态为"未验证"，触发验证流程
5. 如果版本号已知且适配状态为"已验证"，正常启动

这个机制的局限性在于只能检测大版本号（如5.7），无法感知小版本热修复中的具体变更。例如v5.71可能包含重要的UI微调，但版本号与v5.7相同，可能逃过检测。对此，Agent应在启动验证之外辅以运行时异常检测作为补充。

**UI元素校验**：Agent维护一套关键UI元素的基准模板，包括位置、外观、交互响应等。每次运行时，Agent会抽样检查这些元素是否存在且位置正确。校验范围包括：

- 派蒙菜单(M键)的各个入口按钮（设置、角色、背包、地图、任务、祈愿等）
- 圣遗物界面的各装备槽位（生之花、死之羽、时之沙、空之杯、理之冠）
- 副本入口的确认按钮（开始挑战、快速挑战等）
- 角色切换栏的四个角色头像位置
- 小地图的方向指示和传送追踪标记
- 技能冷却的图标显示区域

校验采用分级策略：启动时校验A级元素（核心菜单入口），运行中每10分钟校验B级元素（战斗相关UI），每小时校验C级元素（辅助功能UI）。校验失败可能意味着UI发生了变更，系统会记录具体的失败信息并触发调查流程。

**运行时异常检测**：Agent在运行过程中持续监控操作的成功率。监控指标包括：点击操作的成功率、菜单导航的成功率、技能释放的确认率、传送导航的到达率、物品使用的确认率。如果某个操作在短时间内反复失败（例如连续3次点击未命中目标），系统会标记为异常并触发调查。异常检测使用滑动窗口统计，窗口大小为最近20次操作，当失败率超过30%时触发变更怀疑。

**定期健康检查**：Agent每30分钟执行一次核心感知功能的健康检查。检查内容包括：

1. 关键UI元素的可见性（派蒙菜单是否可打开、地图是否可显示）
2. 核心检测器的置信度（YOLO检测器对已知目标的平均置信度是否在正常范围）
3. 输入响应的正确性（键盘按键是否产生预期的游戏内效果）
4. 截屏功能的可用性（DXcam/MSS是否正常抓取画面）
5. 时钟同步状态（游戏时间与系统时间是否同步）

每项检查产生一个0-100的健康分数，五项的平均分低于70时认为可能发生了影响核心功能的变更。健康检查的结果会记录到日志中供后续分析。

### 2.2 被动检测

被动检测是指Agent通过观察运行过程中的异常表现来发现版本变更。这种方式不需要额外的检测操作，而是依赖运行数据的分析。被动检测是主动检测的重要补充，能够发现主动检测遗漏的变更。

**操作失败率异常上升**：如果Agent执行某个技能序列或导航序列的失败率突然上升（如从5%上升到30%），这可能是UI变更导致的。例如一个原本可靠的攻击后摇取消序列突然失败，可能是因为攻击动画帧数发生了微调，或者确认对话框的响应时间发生了变化。

Agent为每种操作类型维护独立的失败率统计。统计维度包括：
- 按操作类型分：点击、拖拽、按键、菜单导航、技能释放
- 按场景类型分：战斗、探索、资源管理、任务执行
- 按时间窗口分：最近10次、最近100次、当日累计

当任一维度的失败率超过阈值时触发变更怀疑。阈值根据操作类型的基线失败率动态设置，一般为基线值的3倍标准差。例如，菜单导航的基线失败率为2%，标准差为1%，则阈值为5%。

**感知置信度持续偏低**：YOLO检测器和其他视觉感知组件会输出每次检测的置信度分数。如果某个元素（如角色头像、HP条、技能图标）的平均置信度持续偏低，可能是因为该元素的视觉外观发生了改变。

置信度监控的具体实现包括：
- 对每种检测类别维护最近100次检测的置信度均值和方差
- 当最近20次检测的均值低于历史均值的70%时触发警告
- 当最近50次检测的均值低于历史均值的50%时触发变更怀疑
- 对于新增的检测类别（之前从未见过的类别），直接标记为需要验证

Agent维护每种感知类型的置信度基线，当实际置信度偏离基线超过阈值时触发调查。

**新出现的未识别UI元素**：当屏幕上出现Agent无法归类到已知类别的UI元素时（如新的对话框、新的图标、新的进度条），系统会记录并报告这些元素。虽然这些元素不一定是版本变更导致的（也可能是游戏内的临时内容），但它们的存在可以提示可能的UI更新。

未识别元素的处理流程包括：
1. 截取包含未知元素的屏幕区域
2. 记录元素的位置、大小、颜色特征
3. 尝试通过上下文推断元素的功能（例如在圣遗物界面出现的新按钮可能与强化功能相关）
4. 将未知元素信息加入待确认队列
5. 如果同一未知元素在多次运行中反复出现，提高其优先级

**画面特征显著变化**：通过比较当前画面与历史画面的统计特征，Agent可以发现游戏整体视觉风格的显著变化。使用的统计特征包括：

- 颜色直方图：比较RGB三通道的颜色分布变化。新区域开放通常会导致整体色调改变（如稻妻的深蓝色调、须弥的绿色调、枫丹的蓝绿色调）
- 边缘密度：检测画面中边缘的密度和方向分布。新区域的地形特征可能显著不同
- 纹理复杂度：使用灰度共生矩阵计算纹理复杂度指标
- 亮度分布：整体亮度的均值和方差变化

当上述任一特征的偏差超过阈值（如颜色直方图的巴氏距离超过0.3）时，系统认为画面发生了显著变化。这种变化可能对应新区域开放或大规模UI改版。

### 2.3 外部信号

外部信号是指来自Agent系统外部的信息来源，包括官方公告、社区讨论和用户输入。外部信号是主动和被动检测的重要补充，能够提供关于未来变更的提前预警。

**版本公告监控**：Agent通过定期搜索原神官方更新日志、版本前瞻内容等方式获取即将发布或刚刚发布的版本信息。监控频率为：版本前瞻直播前后每天搜索一次，版本更新当天每2小时搜索一次，正常运行期间每周搜索一次。信息来源包括米游社公告、官方网站、HoYoLAB、版本前瞻直播文字版等。

从公告中提取的关键信息包括：版本号和更新日期、新增区域和内容概述、UI系统变更说明、机制调整详情、已知Bug列表。这些信息帮助Agent提前准备可能的变更适应。例如，如果公告提到"圣遗物界面优化"，Agent可以提前准备圣遗物相关UI的重新校准。

**社区反馈收集**：玩家社区（如NGA、原神贴吧、B站评论区、Reddit r/Genshin_Impact）会快速讨论新版本的变化和问题。Agent搜索相关社区讨论帖，提取与版本变更相关的关键词和描述，与Agent的能力列表交叉对比，标记可能受影响的Agent能力。社区信息的准确性参差不齐，建议至少从三个独立来源确认同一变更信息后才纳入处理。

**用户手动通知**：用户是最直接的反馈来源。当用户发现Agent在某方面表现异常时，可以通过反馈机制告知Agent。Agent提供的反馈渠道包括：快捷键报告（如按F10标记当前操作异常）、文字描述报告、截图报告（自动捕获当前屏幕状态）。Agent收到反馈后记录时间、场景、操作步骤和用户描述，自动截取相关屏幕状态，分析可能的变更原因，如果确认为版本变更影响则标记对应能力为"待修复"。

## 第三章：兼容性适配策略

针对不同类型的版本变更，Agent采用不同的适配策略，确保系统在版本更新后仍能正常运行。

### 3.1 UI适配层

UI适配层的目标是让Agent能够在UI发生改变时仍能正确定位和操作界面元素。

**相对坐标系统**：Agent不使用绝对像素坐标来定位UI元素，而是使用相对于界面特征元素的偏移量。例如，技能按钮的位置不是(1200, 650)，而是"派蒙菜单右侧第二个图标下方30像素"。这种系统需要维护一个界面特征元素列表，作为所有相对定位的基准。

相对坐标系统的核心概念：
- 锚点元素（Anchor）：每个界面有一个或多个锚点，锚点是稳定且易于识别的元素（如对话框的标题栏、菜单的背景边框等）
- 相对偏移（Offset）：目标元素相对于锚点的像素偏移量
- 比例因子（Scale Factor）：根据当前分辨率与基准分辨率的比值，自动缩放偏移量

优点是即使界面整体缩放，相对位置仍然有效。缺点是需要准确识别基准元素本身。为了提高鲁棒性，系统采用多锚点冗余策略：每个目标元素定义相对于2-3个不同锚点的偏移，当主锚点识别失败时可以使用备用锚点。

**视觉特征匹配**：对于每个关键UI元素，Agent维护的不只是坐标，而是一组视觉特征描述（包括颜色分布、边缘形状、与其他元素的空间关系等）。当需要定位一个元素时，Agent会在预期区域搜索与特征描述匹配的元素，而不是简单地在固定坐标读取。

视觉特征描述的结构包括：
- 颜色直方图特征：元素的主色调分布（如确认按钮的主色为蓝色，取消按钮的主色为灰色）
- 边缘特征：元素的轮廓形状描述（如按钮的圆角矩形、图标的几何形状）
- 空间关系特征：与周围元素的位置关系（如在技能图标E的右侧、在HP条的下方）
- 文本特征：如果元素包含文字，还记录文字内容（通过OCR验证）

匹配过程分为两个阶段：粗定位（使用空间关系特征缩小搜索范围）和精匹配（使用颜色和边缘特征在粗定位区域内确认目标）。这种方法可以应对图标样式变更和微小幅移。

**UI元素版本化注册表**：Agent维护一个UI元素版本化注册表，记录每个版本的游戏界面布局描述。注册表结构包括：版本号、区域名称、界面类型、元素名称、特征描述、相对坐标等信息。当检测到当前版本时，系统从注册表加载对应的布局描述。

注册表的数据结构设计如下：

```yaml
# UI元素版本化注册表示例
version: "5.7"
interfaces:
  paimon_menu:
    anchor: "menu_background"
    elements:
      - name: "settings_button"
        offset: [120, 340]
        features:
          color: "blue_grey"
          shape: "rounded_rect"
          text: "设置"
      - name: "character_button"
        offset: [120, 280]
        features:
          color: "blue_grey"
          shape: "rounded_rect"
          text: "角色"
  character_menu:
    anchor: "character_model_display"
    elements:
      - name: "skill_e"
        offset: [-200, 150]
        features:
          shape: "skill_icon"
          position_hint: "left_side_panel"
      - name: "artifact_slot_flower"
        offset: [100, -50]
        features:
          shape: "slot_outline"
          position_hint: "right_panel_top"
```

当检测到新版本但注册表中没有对应记录时，系统会尝试加载最近的已知版本配置作为初始估计，然后执行自动校准来修正差异。

**自动重新校准流程**：当检测到UI变更时，Agent可以启动自动重新校准流程。校准流程的设计原则是安全优先，不执行任何可能导致游戏内状态改变的操作。

校准流程的具体步骤：
1. 暂停所有主动操作，进入只读观察模式
2. 逐个打开已知菜单（Esc、C、B、M等），截取每个菜单的完整界面
3. 对每个截图执行元素检测，使用多尺度滑动窗口搜索已知元素
4. 对于找到的元素，记录新的位置信息
5. 对于未找到的元素，扩大搜索范围再次尝试
6. 更新本地位置记录
7. 重新执行步骤2-6验证更新后的位置是否正确
8. 对于仍无法定位的元素，标记为"需要人工确认"

这种流程的局限是可能无法处理复杂的布局变化（如菜单从垂直布局改为水平布局），但可以处理大部分常见的按钮位移和图标微调。

### 3.2 机制适配层

机制适配层的目标是让Agent能够理解和适应游戏核心玩法的变化。

**机制抽象接口**：Agent的战斗和任务系统通过抽象接口与具体的游戏机制交互。例如，元素反应不直接硬编码雷+火=超载，而是定义为一个反应查找表，支持动态添加新反应类型。这种设计允许在版本更新添加新元素反应时，只需更新数据而不修改代码。

抽象接口的设计遵循以下原则：
- 所有游戏机制通过Protocol（协议类）定义，不使用具体的实现类
- 每种机制有明确的输入（触发条件）和输出（效果结果）定义
- 机制之间的交互通过事件系统解耦，避免直接的函数调用依赖
- 新增机制只需要实现对应的Protocol接口，不需要修改已有的调用代码

元素反应查找表的数据结构示例：

```yaml
# 元素反应查找表
elemental_reactions:
  - trigger: ["pyro", "hydro"]
    result: "vaporize"
    visual_effect: "steam_cloud"
    damage_multiplier: 1.5  # 水触发蒸发
    priority: 10

  - trigger: ["hydro", "pyro"]
    result: "vaporize"
    visual_effect: "steam_cloud"
    damage_multiplier: 2.0  # 火触发蒸发
    priority: 10

  - trigger: ["dendro", "electro"]
    result: "quicken"
    visual_effect: "green_spark"
    damage_multiplier: 0.0  # 激化本身不造成伤害
    sub_reactions:
      - "aggravate"  # 超激化
      - "spread"     # 蔓激化
    priority: 20
    added_in_version: "3.0"
```

通过这种结构，3.0版本添加草元素反应时，只需要在查找表中新增条目，而不需要修改战斗系统的核心代码。

**新机制的学习路径**：当Agent遇到未知的游戏机制时（如5.0版本的夜魂系统），它会启动探索性学习流程。学习路径分为四个阶段：

阶段一——观察（被动模式）：Agent不主动操作，只记录新机制的视觉表现。记录内容包括：新UI元素的外观和位置、新特效的颜色和形态、新状态条的样式和数值范围。观察阶段的目的是收集足够的信息以便后续分析。

阶段二——试探（安全模式）：Agent在确保安全的前提下（如角色处于安全区域、HP满状态），尝试与新机制交互。试探操作包括：尝试按键触发（E键、Q键等）、尝试与UI元素交互（点击、长按）、尝试在特定条件下触发（移动中、战斗中）。每次试探都记录触发条件和结果。

阶段三——归纳（分析模式）：基于观察和试探收集的信息，Agent尝试归纳新机制的行为模式。归纳内容包括：触发条件的总结、效果结果的分类、状态转换的规则、与其他机制的交互。归纳结果以结构化格式存储，方便后续使用。

阶段四——验证（测试模式）：Agent在实际场景中验证归纳结果的正确性。如果验证通过，将新机制知识正式纳入知识库；如果验证失败，返回阶段二继续探索。整个过程可能需要多次迭代。

**机制参数热更新**：Agent的战斗策略和任务参数存储在外部配置文件中，允许在不修改代码的情况下调整策略参数。热更新参数的类别包括：战斗参数（元素反应触发优先级、技能释放时机）、导航参数（传送点选择策略、路径规划权重）、感知参数（检测置信度阈值、跟踪参数）、策略参数（战斗风格选择、资源使用策略）。热更新通过监听配置文件变化实现，当配置文件被修改时Agent自动重新加载参数，无需重启。

### 3.3 内容适配层

内容适配层的目标是让Agent能够处理游戏内容的持续增加，无需频繁修改代码。

**内容数据与代码分离**：Agent维护一套内容数据库，存储所有可识别内容的信息（区域、角色、武器、圣遗物、Boss、资源点等）。这些数据以结构化格式（如YAML或JSON）存储，与执行代码分离。新内容（如新角色、新区域）通过更新数据文件注入，无需修改核心逻辑。

内容数据库的Schema设计如下：

```yaml
# 角色数据示例
characters:
  - name: "玛拉妮"
    element: "hydro"
    weapon_type: "catalyst"
    rarity: 5
    version_added: "5.0"
    region: "natlan"
    skills:
      - name: "元素战技"
        key: "E"
        cooldown: 6.0
        visual_effect: "shark_surf"
        nightsoul: true
        nightsoul_cost: 5.0  # 每秒消耗
      - name: "元素爆发"
        key: "Q"
        energy_cost: 60
        visual_effect: "wave_bite"
    mechanics:
      - type: "nightsoul_blessing"
        trigger: "E_skill"
        resource: "nightsoul_points"
        max_points: 80
```

通过这种结构，新角色的所有信息都可以通过数据文件描述，无需为每个新角色编写专门的代码。

**内容补丁系统**：当游戏版本更新时，Agent可以加载对应的内容补丁包。补丁包包含该版本的新增内容信息和变更的内容信息。补丁包的格式设计为可合并的，允许累积更新。Agent维护版本到补丁的映射，确保加载正确版本的数据。

补丁包的结构设计：
- 补丁元数据：版本号、发布日期、前置版本要求
- 新增内容：本次版本新增的所有内容条目
- 变更内容：本次版本修改的已有内容条目（如数值调整）
- 删除内容：本次版本移除的内容条目（如过期的活动）
- UI变更：本次版本涉及的UI布局变更描述
- 机制变更：本次版本涉及的机制参数变更

补丁包的加载顺序严格按版本号递增执行，不允许跳版本加载。例如从v5.0升级到v5.3时，需要依次加载v5.1、v5.2、v5.3的补丁包。每加载一个补丁包后执行完整性校验，确保数据状态正确。

**内容发现模式**：当Agent遇到数据库中不存在的内容时（如新版本的采集物），它会进入发现模式。发现模式包括：记录该内容的外观特征和出现位置、尝试与该内容交互以理解其用途、将发现结果存入待确认队列供后续验证。发现的内容在经过人工确认后，会被正式纳入内容数据库。

## 第四章：版本迁移框架

版本迁移框架定义了从旧版本适配到新版本的完整流程，包括迁移前、迁移中和迁移后三个阶段。

### 4.1 迁移前（版本更新前一天）

迁移前阶段的目的是在版本实际更新前做好准备，降低迁移风险。

**保存当前状态检查点**：在版本更新前，Agent将当前的完整状态保存为检查点。检查点内容包括：所有UI元素的位置记录、检测模型的参数配置、内容数据库的当前版本、运行时统计信息等。保存检查点的目的是在迁移失败时能够回退到已知的稳定状态。

检查点的完整内容包括：
- UI元素位置表：所有已记录的UI元素在当前版本中的位置和特征
- 检测模型快照：YOLO模型的当前权重、阈值配置、类别映射表
- 内容数据库版本：当前加载的所有内容数据文件的版本哈希
- 感知参数配置：所有视觉感知组件的当前参数
- 战斗策略配置：当前的战斗策略参数和优先级设置
- 运行时统计：最近7天的操作成功率、失败模式统计
- 用户自定义配置：用户手动调整的所有参数

检查点以时间戳命名存储在专门的检查点目录中。系统保留最近5个检查点，超过5个时自动清理最旧的检查点。检查点的存储格式为压缩的JSON文件，便于快速加载和比对。

**搜索更新内容摘要**：Agent通过搜索原神官方公告和版本前瞻内容，获取即将发布版本的主要变更信息。摘要内容包括：新区域开放、新角色机制、新UI系统、已知问题等。这些信息帮助预判可能受影响的能力范围。

搜索的优先信息源和其可靠性排序：
1. 官方版本更新公告（米游社/官网）——最高可靠性
2. 版本前瞻直播文字总结——高可靠性，但可能包含未最终确认的内容
3. 测试服（Beta）数据挖掘结果——中等可靠性，正式版可能修改
4. 社区攻略和讨论——低可靠性，需交叉验证

从搜索结果中提取的关键信息类型：
- 新增系统/机制列表（例如"新增夜魂系统"）
- UI界面变更说明（例如"圣遗物界面优化"）
- 区域开放信息（例如"开放纳塔地区"）
- 角色和武器变更（例如"新角色玛拉妮"）
- 已知Bug和修复（例如"修复了XX功能的异常"）
- 数值平衡调整（例如"XX角色技能伤害提升"）

**预判可能受影响的能力**：基于收集到的更新摘要，Agent分析哪些能力可能受到影响。例如，如果新版本涉及圣遗物UI改版，系统会标记圣遗物相关的所有能力为高风险；如果新版本是纯内容更新（如新增一个活动副本），则标记的风险较低。

预判分析使用规则引擎实现，每条规则定义了变更关键词到受影响能力的映射：

| 更新关键词 | 受影响的Agent能力 | 风险等级 |
|-----------|-----------------|---------|
| 圣遗物优化/改版 | 圣遗物管理、圣遗物强化、圣遗物锁定 | 高 |
| 新元素反应 | 战斗策略、元素反应识别 | 高 |
| 新区域/新地图 | 探索导航、传送系统 | 中 |
| 新角色 | 角色识别、技能识别 | 低 |
| 新Boss | Boss检测、战斗策略 | 中 |
| 设置菜单调整 | UI导航、系统配置 | 中 |
| 性能优化 | 时序控制、输入延迟 | 低 |

**准备降级策略**：对于高风险的能力，Agent准备降级策略。降级策略包括：暂时禁用受影响的能力、切换到更保守的操作模式、增加额外的验证步骤等。降级策略的目标是在迁移初期保持系统稳定，避免因未知变更导致的失败。

降级策略的分级定义：

一级降级（预防性降级）：在版本更新后的前24小时内自动启用。包括：为所有高风险操作增加确认步骤（操作前截屏验证），降低操作执行速度（增加操作间隔），启用详细日志记录。

二级降级（响应性降级）：当检测到操作失败率上升时启用。包括：暂时禁用失败的操作类型，切换到备用操作方式（如从自动操作切换到半自动），向用户提示当前处于降级模式。

三级降级（紧急降级）：当核心功能完全失效时启用。包括：停止所有主动操作，仅保留监控功能，向用户报告需要人工介入，准备回退到上一个已知稳定状态。

### 4.2 迁移中（版本更新后首次启动）

迁移中阶段是版本迁移的关键窗口，需要在短时间内完成多个检测和适配任务。

**版本检测和变更识别**：Agent启动后首先确认游戏版本号，与迁移前保存的预期版本对比。如果版本号匹配预期，说明更新正常；如果不匹配（如版本号未知或与预期不符），说明可能需要额外的适配工作。

**UI自动校准流程**：在版本确认后，Agent执行UI自动校准流程。流程从已知的界面锚点（如派蒙菜单、角色菜单）开始，逐区域验证UI元素的存在性和位置。对于发现位置变化的元素，更新本地记录；对于完全消失的元素，标记为需要人工确认；对于新出现的元素，尝试识别其功能。

**核心功能验证测试**：校准完成后，Agent执行核心功能的验证测试。测试内容包括：关键UI元素的点击响应、技能释放的视觉反馈、角色切换的动画确认、导航到传送点的路径验证等。测试结果用于判断系统是否已经可以正常工作。

**受影响场景标记**：根据验证测试结果，Agent标记仍存在问题的场景为"待修复"。每个待修复场景关联具体的错误表现、可能的变更原因、建议的修复方向。标记结果用于指导后续的修复工作。

### 4.3 迁移后（更新后第一次完整运行）

迁移后阶段是验证迁移成功的最后阶段，需要在实际任务中验证系统的完整性。

**所有场景的验证性测试**：Agent按优先级逐一验证每个场景的可用性。验证内容包括：日常任务执行（如每日委托、派遣）、探索任务执行（新区域探索）、战斗任务执行（新Boss挑战）、资源管理操作（圣遗物更换、武器强化）等。每个场景的验证结果都记录在案。

**新内容探索和记录**：在场景验证的同时，Agent对新内容进行探索和记录。探索内容包括：新区域的传送点和资源分布、新角色的技能特效和输出循环、新武器和圣遗物的获取路径等。探索结果用于更新本地知识库。

**更新状态数据库**：完成验证和探索后，Agent更新状态数据库。更新内容包括：新版本的UI布局记录、新内容的知识库条目、检测模型的新增类别、历史测试结果等。状态数据库的更新确保后续运行能够利用本次迁移的成果。

**向用户报告兼容性状态**：Agent向用户报告本次迁移的总体状态。报告内容包括：成功迁移的场景数量、仍存在问题的场景及建议、发现的新内容概述、建议的后续操作等。报告帮助用户了解系统当前状态并做出下一步决策。

## 第五章：持续学习机制

持续学习机制确保Agent能够随着时间推移不断积累关于游戏的知识，提高对版本变更的适应能力。

**新内容的自动探索策略**：当Agent在游戏中遇到未知内容时，它会执行系统化的探索流程。探索策略包括：首先观察内容的外观和出现位置，然后尝试与其交互（如果是可交互的），最后归纳内容的功能和用途。探索过程使用安全优先原则，避免可能导致角色死亡的冒险操作。探索结果存储到知识库供后续使用。

自动探索策略的安全约束：不得在战斗中尝试未知操作；不得在限时任务中尝试未知操作；仅在安全区域（如城镇、已探索的开放区域）中进行探索；探索过程中角色HP低于50%时立即中止；每次探索时间不超过5分钟。

自动探索的优先级排序：高频出现但无法识别的内容优先学习；与当前任务相关但无法识别的内容次之；新区域中出现的内容再次之；已知区域中新出现的内容最后。

**玩家社区知识获取**：Agent定期搜索玩家社区的攻略和讨论，提取与操作相关的信息。例如，社区攻略可能提供某个复杂机制的详细解析，某个新区域的快速跑图路线，或者某个新Boss的弱点分析。Agent从这些信息中提取可以转化为操作知识的部分，补充其知识库。知识来源包括米游社、NGA、贴吧、B站等平台。

社区知识获取的处理流程：
1. 定期搜索社区内容（每周一次，版本更新前后增加频率）
2. 识别与操作相关的攻略和讨论帖（过滤纯剧情讨论和吐槽帖）
3. 提取关键操作信息（如Boss弱点、元素反应顺序、UI操作步骤）
4. 将提取的信息转化为结构化的操作知识（如ActionBlock模板）
5. 验证转化后的操作知识是否正确（通过Dry-Run模拟）
6. 将验证通过的知识纳入正式知识库

信息提取注意事项：不同平台的攻略质量参差不齐，需交叉验证；攻略中的操作描述可能不够精确，需要模糊匹配；版本号标注可能不准确，需确认攻略对应的游戏版本；部分攻略可能包含过时信息。

**失败案例的反向学习**：每次操作失败后，Agent执行反向学习流程。流程包括：分析失败的根本原因（是检测错误、坐标偏差、策略不当还是未知变更）、记录失败的场景和失败前的状态、总结避免失败的方法、更新相关策略或参数。反向学习的目的是确保同样的失败不会重复发生。

反向学习的分析维度：
- 感知层面：是否因为检测器未能识别目标？（置信度过低、目标被遮挡、视觉特征变化）
- 规划层面：是否因为策略选择不当？（错误的元素反应顺序、不合适的战斗策略）
- 执行层面：是否因为操作执行失败？（点击偏移、按键延迟、输入丢失）
- 环境层面：是否因为环境因素？（网络延迟、帧率下降、加载画面超时）

每种失败维度对应不同的学习策略：
- 感知层失败：更新检测模型或调整置信度阈值
- 规划层失败：更新策略参数或调整优先级
- 执行层失败：调整操作时序或修正坐标偏移
- 环境层失败：增加重试机制或调整超时参数

**学习成果的版本化管理**：Agent的每个学习成果都与特定的版本绑定。当游戏版本更新时，过时的学习成果可能失效，需要重新验证或更新。版本化管理的目的是确保Agent不会使用来自不兼容版本的知识。例如，某个圣遗物UI的位置知识只在4.3到4.5版本有效，4.6版本该UI发生了改变，需要重新学习。

版本化知识的管理规则：每条知识记录都标注"生效版本范围"和"最后验证版本"；版本更新后对所有知识记录执行兼容性检查；标注为"自动验证"的知识系统自动重新测试；标注为"人工验证"的知识标记为"待确认"并通知用户；超过3个版本未验证的知识自动降级为"不确定"状态。

版本化知识的格式示例：

```yaml
knowledge_entry:
  id: "k_ui_artifact_enhance_button"
  type: "ui_position"
  content: "圣遗物强化确认按钮位于界面底部中央"
  version_range: ["4.3", "5.7"]
  last_verified: "5.7"
  verification_method: "auto"
  confidence: 0.95
  related_entries:
    - "k_ui_artifact_slot_flower"
    - "k_ui_artifact_lock_button"
```

## 第六章：版本兼容性矩阵

版本兼容性矩阵定义了每种场景对不同类型版本变更的敏感度，指导迁移工作的优先级分配。

### 6.1 敏感度定义

场景对版本变更的敏感度分为三级：低敏感、中敏感、高敏感。

**低敏感场景**：这类场景几乎不受版本变更影响，可以长期稳定运行。主要包括：基础输入操作（键盘按键、鼠标移动）、非UI相关的时序控制、环境音视频监控等。示例场景包括角色移动控制、视角旋转控制。

**中敏感场景**：这类场景对特定类型的版本变更敏感，但可以通过自动适配处理。主要包括：依赖UI布局的操作、依赖视觉识别的检测等。示例场景包括菜单导航（对按钮位置敏感）、道具使用（对道具图标敏感）。中敏感场景通常可以通过相对坐标和视觉特征匹配实现自动适配。

**高敏感场景**：这类场景对多种类型的版本变更都敏感，且可能需要人工介入才能恢复功能。主要包括：依赖特定机制的战斗策略、依赖特定内容数据的任务执行等。示例场景包括元素反应战斗（对新元素反应敏感）、特定区域探索（对新区域开放敏感）。高敏感场景需要更仔细的迁移验证。

### 6.2 变更类型与场景映射

| 变更类型 | 低敏感场景 | 中敏感场景 | 高敏感场景 |
|---------|-----------|-----------|-----------|
| UI按钮位置移动 | 角色移动、视角旋转 | 菜单导航、设置调整 | 圣遗物更换、武器强化 |
| 新增/删除菜单项 | 角色移动、视角旋转 | 菜单导航 | 合成系统、新功能使用 |
| 图标样式变更 | 角色移动、视角旋转 | 道具识别、图标检测 | 无直接场景 |
| 新元素/新反应 | 角色移动、视角旋转 | 元素反应识别 | 激化反应战斗、草元素反应 |
| 新战斗机制 | 角色移动、视角旋转 | 战斗状态识别 | 芒荒战斗、夜魂战斗 |
| 新区域开放 | 角色移动、视角旋转 | 区域识别 | 区域探索、任务执行 |
| 新角色/新武器 | 角色移动、视角旋转 | 角色识别 | 角色切换、技能释放 |
| 系统性能变化 | 所有场景 | 无特殊 | 无特殊 |

### 6.3 兼容状态判定

根据场景敏感度和实际变更情况，系统可以处于以下兼容状态：

**完全兼容**：所有高敏感场景都通过验证，系统可以正常运行。用户可以继续正常使用所有功能，无需额外操作。兼容状态为绿色，系统正常运行。

**部分兼容**：部分高敏感场景验证失败，但中低敏感场景正常工作。系统处于降级模式，失败的场景暂时禁用，其他功能正常。用户可能需要等待补丁更新或手动调整配置。兼容状态为黄色，系统发出警告。

**不兼容**：多个高敏感场景验证失败，或者关键系统（如UI检测）完全失效。系统进入保护模式，停止所有主动操作。用户需要等待新版本的适配更新，或者回退到之前的游戏版本。兼容状态为红色，系统停止运行。

### 6.4 安全忽略判定

并非所有版本变更都需要Agent响应。以下变更可以安全忽略，不影响任何Agent场景：

- 纯剧情文本新增或修改（Agent不处理剧情内容）
- 限时活动的UI布局（活动结束后自动消失）
- 角色语音包更新（Agent不使用语音识别）
- 音乐和音效变更（Agent的感知不依赖音频）
- 纯视觉装饰更新（如节日主题界面，功能不变）
- 多语言文本修正（Agent使用固定语言版本）
- 社交功能更新（如好友系统、聊天系统）
- 纯客户端Bug修复（如果不影响Agent使用的功能）

### 6.5 降级处理判定

以下变更影响少量场景，可以通过降级方式处理：

- 新增的角色/武器/圣遗物（Agent暂时不识别新内容，但不影响对已有内容的处理）
- 新增的区域和传送点（Agent暂时不探索新区域，但在已知区域正常工作）
- 非核心UI的微调（如背景色变化、字体调整，不影响功能操作）
- 战斗数值平衡调整（如伤害系数变化，Agent调整策略参数但不改变操作方式）
- 新增的采集物种类（Agent暂时不采集新类型，但继续采集已知类型）

### 6.6 人工介入判定

以下变更影响核心功能，需要人工介入处理：

- 游戏窗口标题或进程名变更（影响SafeWindowBackend的窗口匹配）
- 反作弊系统升级导致截屏或输入被阻止（需要重新评估安全边界）
- 游戏渲染引擎升级导致画面输出格式变化（影响所有视觉感知组件）
- 核心菜单结构大幅重组（如派蒙菜单完全重新设计）
- 游戏输入系统变更（如新增输入过滤或延迟）
- 游戏分辨率/FOV参数变更（影响CameraServo的参数配置）

以下是当前版本（v5.7）各场景的兼容性状态示例：

## 第七章：历史版本变更案例

通过分析原神历史上五个重大版本变更的实际情况，我们可以更好地理解版本变更对Agent的影响，并设计相应的适配方案。

### 7.1 2.0稻妻开放

**变更内容**：2021年7月21日，原神开放了稻妻区域，引入了全新的雷元素机制系统。主要变更包括：开放鸣神岛、神无冢、八酝岛三个新区域；引入雷种子系统，玩家可以通过雷樱枝条获取雷种子，用以穿越若雷结界、抵御雷祸；引入雷极系统，提供快速移动能力；新增神樱眷顾声望系统；新增雷元素相关的谜题机制（若雷石、雷霆探针、放电石、聚电石等）。

**受影响的Agent能力**：稻妻区域的开放主要影响探索相关能力。雷种子系统要求Agent能够识别雷樱枝条的位置并正确交互；雷祸机制要求Agent在进入高雷元素浓度区域前先获取雷种子；雷极系统要求Agent在需要快速移动的场景中合理使用雷极；雷元素的若雷结界要求Agent在遇到屏障时知道需要雷种子才能进入。此外，稻妻区域的整体导航需要重新建立，包括传送点位置、采集物分布、NPC位置等信息。

**理想的适配方案**：版本更新前，系统应该通过官方公告了解稻妻开放的基本信息，并准备雷种子相关的视觉识别模型。版本更新后，系统首先通过探索建立稻妻区域的地图数据库，包括传送锚点位置、重要NPC位置、资源点分布等。然后更新雷种子相关知识，包括雷樱枝条的外观、获取方式、使用方法等。最后验证雷祸区域的识别和防护策略是否正确执行。整个过程中，系统需要对新区域保持探索优先级，逐步完善其在该区域的执行能力。

### 7.2 3.0须弥开放

**变更内容**：2022年8月24日，原神开放了须弥区域，引入了全新的草元素反应体系。主要变更包括：开放道成林、护世森、阿陀河谷、善见地、二净甸、桓那兰那六个新区域；引入草元素和两大类新反应（激化反应包括超激化和蔓激化，绽放反应包括绽放、超绽放、烈绽放）；引入死域机制，玩家在死域中会持续积累凋零状态，需要通过生之烛等方式削弱；引入桓那兰那的梦之树声望系统；新增多种草元素相关的谜题和机关。

**受影响的Agent能力**：草元素系统的引入深刻影响了Agent的战斗能力。首先，Agent需要识别和理解激化反应的视觉表现（被激化目标会显示特殊的光环效果），并在战斗决策中考虑激化带来的额外伤害。其次，绽放反应引入了草元素种子的概念，Agent需要理解种子的生成、成长和爆炸机制，并据此调整元素反应顺序。再次，死域机制要求Agent能够识别死域区域并在进入前准备应对凋零的策略。最后，新的草元素角色（如提纳里、柯莱）需要新的识别模型和输出循环。

**理想的适配方案**：版本更新前，系统应该通过版本前瞻了解草元素反应的基本机制，特别是激化和绽放的触发条件和效果。版本更新后，系统需要更新元素反应的查找表，添加草元素相关的所有反应类型。同时需要建立草元素种子和死域的视觉识别能力。在战斗策略方面，系统需要学习激化队的输出手法（雷元素角色起手→草元素角色触发激化→其他角色收割），以及绽放队的元素顺序（水元素先手→草元素触发绽放→火或雷元素触发超绽放或烈绽放）。整个适配过程中，战斗策略的更新是最大的挑战，需要详细的测试验证。

### 7.3 4.0枫丹开放

**变更内容**：2023年8月16日，原神开放了枫丹区域，引入了全新的水下探索和芒荒机制。主要变更包括：开放枫丹廷、白浅区、厄唾卡、纳西地区等新区域；引入水下探索系统，玩家可以在枫丹的水域中进行游泳、潜水等探索活动；引入芒荒机制，枫丹的部分怪物和机关具有芒或荒的属性，使用相反属性攻击可以使怪物瘫痪；引入谕示裁定系统，这是一种枫丹特有的任务和审判机制；新增始基力概念，枫丹角色可以使用芒性或荒性的攻击。

**受影响的Agent能力**：枫丹区域的开放带来了两方面的主要挑战。水下探索要求Agent能够理解和操作水下运动机制，包括潜水、氧气管理、水下交互等。芒荒机制要求Agent能够识别怪物的芒荒属性，并据此选择对应属性的角色或攻击方式。具体来说，使用芒属性攻击荒属性怪物（或反之）可以使其进入瘫痪状态，这是一种高效的战斗策略。Agent需要建立芒荒属性的视觉识别能力，并在战斗决策中考虑属性匹配。

**理想的适配方案**：版本更新前，系统应该通过搜索了解芒荒机制的基本概念和战斗应用。版本更新后，系统需要建立芒荒属性的视觉识别模型，包括怪物体上的芒荒标识、芒荒能量块的外观等。在战斗方面，系统需要更新战斗策略库，为枫丹区域的怪物添加芒荒属性标注，并在策略选择时考虑属性匹配。例如，面对荒属性的发条机关时，系统应该优先选择芒属性的角色（如林尼、菲米尼）。水下探索方面，系统需要学习水下运动的控制逻辑和氧气管理策略。整个适配过程中，芒荒机制的视觉识别是最大的技术挑战。

### 7.4 5.0纳塔开放

**变更内容**：2024年8月28日，原神开放了纳塔区域，引入了全新的夜魂机制。主要变更包括：开放纳塔的多个新区域；引入夜魂和燃素机制，纳塔角色可以通过元素战技进入夜魂加持状态，夜魂值耗竭后会消耗燃素来维持；引入夜魂传递机制，在特定移动状态下（如冲刺、游泳、攀爬、滑翔）切换纳塔角色可以直接进入夜魂加持状态；引入夜魂迸发效果，当队伍中有纳塔角色时，对敌人造成元素伤害后会触发夜魂迸发；新增嵴峰龙、匿叶龙、鳍游龙等幻化龙形态，提供独特的大世界移动能力。

**受影响的Agent能力**：夜魂机制是5.0版本最复杂的系统变更，影响多个方面的Agent能力。首先，夜魂状态的识别要求Agent能够识别角色身上的夜魂条和夜魂加持特效。其次，夜魂值的能量管理要求Agent理解夜魂值的消耗和补充机制，合理规划技能释放时机。再次，夜魂传递机制要求Agent能够在执行特定移动动作时及时切换纳塔角色，触发夜魂加持。最后，夜魂迸发效果要求Agent在战斗策略中考虑触发时机和收益。纳塔区域的大世界移动能力也大幅提升，Agent需要学习如何高效利用这些新能力。

**理想的适配方案**：版本更新前，系统应该通过官方前瞻了解夜魂机制的基本概念。版本更新后，系统需要建立夜魂状态的视觉识别能力，包括夜魂条的检测、夜魂加持特效的识别。能量管理方面，系统需要为每种纳塔角色建立状态机模型，包括夜魂值的消耗速度、燃素的补充条件等。战斗策略方面，系统需要学习夜魂迸发的触发条件和效果收益，将其整合到输出循环中。大世界探索方面，系统需要学习幻化龙的触发条件和使用方法，特别是在存在燃素机制的区域中的移动策略。整个适配过程中，夜魂状态机的建立是最复杂的部分，需要为每种纳塔角色设计专门的状态管理逻辑。

### 7.5 圣遗物UI改版

**变更内容**：从4.3版本开始，原神对圣遗物管理和养成界面进行了多次优化。主要变更包括：4.3版本新增圣遗物快速装备功能，可以根据自定义方案自动装配圣遗物；4.4版本进一步优化圣遗物快速装备，支持自定义主属性、套装类型和追加属性；5.5版本引入祝圣之霜机制，定义后的圣遗物在强化到满级时追加属性会至少强化2次；圣遗物强化界面也经历了多次调整，包括阶段放入功能（自动按4/8/12/16级分阶段升级）、快捷放入功能（自动选择最优强化方案）等。

**受影响的Agent能力**：圣遗物UI的多次改版直接影响Agent的资源管理能力。每次UI布局变化都可能导致圣遗物相关操作的失败，如原本点击圣遗物装备槽位的操作可能因布局变化而点到错误的位置。圣遗物快速装备功能的引入改变了圣遗物更换的流程，Agent需要学习使用新的自动装备功能而不是手动操作。阶段放入功能改变了强化操作的方式，Agent需要理解如何使用该功能来提高强化效率。

**理想的适配方案**：版本更新前，系统应该通过版本更新公告了解圣遗物UI的具体变更内容。版本更新后，系统需要重新扫描圣遗物相关的所有界面元素位置，更新本地记录。对于新增的功能（如快速装备、阶段放入），系统需要学习正确的使用流程。整个适配过程中，需要特别注意圣遗物装备槽位、锁定按钮、强化入口等关键元素的位置变化。建议在每次圣遗物UI变更后进行完整的校准测试，确保所有相关操作都能正常执行。

## 附录C：新版本发布检查流程

在每个新版本发布后，按照以下流程执行检查：

```
新版本发布检查流程
===================

阶段1：版本确认（预计耗时：5分钟）
----------------------------------------
1. 启动游戏，确认版本号显示
2. 记录当前版本：v[X.X]
3. 与预期版本对比
4. 如果版本不匹配，标记为异常并报告
5. 加载对应版本的配置文件（如果存在）
6. 如果对应版本的配置不存在，加载最近版本的配置并标记为"未验证"

阶段2：基础功能验证（预计耗时：30分钟）
----------------------------------------
1. 打开派蒙菜单（Esc键），验证菜单正常显示
2. 打开角色菜单（C键），验证角色信息正常显示
3. 打开背包（B键），验证物品列表正常显示
4. 打开地图（M键），验证地图正常显示
5. 执行一次角色移动（W/A/S/D），验证移动控制正常
6. 执行一次普通攻击（左键），验证攻击动画和判定正常
7. 执行一次元素战技（E键），验证技能释放正常
8. 执行一次角色切换（1/2/3/4键），验证切换动画正常
9. 检查小地图显示，验证方向指示和追踪标记正常
10. 检查HP条显示，验证角色和敌人HP条可见

阶段3：UI校准验证（预计耗时：45分钟）
-------------------------------------
1. 逐个验证派蒙菜单的各个入口按钮位置
2. 验证角色菜单的技能图标位置和冷却显示
3. 验证背包的标签切换功能（武器/圣遗物/材料/消耗品）
4. 验证圣遗物界面的装备槽位（5个槽位位置确认）
5. 如发现位置变化，记录新旧位置对比并更新
6. 验证强化界面的按钮位置（强化确认、取消、材料选择）
7. 验证地图的传送锚点标记显示
8. 验证秘境入口的确认按钮位置
9. 截取所有关键界面的参考截图，存入版本截图库

阶段4：场景验证测试（预计耗时：60分钟）
---------------------------------------
优先级A（每日任务相关）：执行一次每日委托完成流程，验证委托追踪功能（V键导航），验证传送功能（M键→选择锚点→确认传送），验证采集物交互（F键拾取）。

优先级B（战斗相关）：执行一次副本挑战完整流程，验证战斗开始→技能释放→敌人击败→结算的完整流程，验证元素反应的视觉反馈是否正确识别，验证角色切换战斗中的响应速度。

优先级C（资源相关）：执行一次圣遗物强化完整流程，验证材料选择功能，验证强化结果确认。

阶段5：兼容性判定（预计耗时：10分钟）
--------------------------------------
根据上述验证结果，判定当前兼容性状态：
- 完全兼容：所有优先级A和B场景通过
- 部分兼容：优先级A场景通过，B/C场景部分失败
- 不兼容：优先级A场景失败

输出最终报告
------------
记录所有发现的问题和建议的修复方向。
如果存在无法自动解决的问题，标记为需要人工介入。
报告格式参见附录A的版本变更影响评估模板。
```
